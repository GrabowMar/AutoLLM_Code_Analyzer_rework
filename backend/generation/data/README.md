# Seed library content (`backend/generation/data/`)

`manage.py seed_library` loads this directory into the library (spec section 11.1); `manage.py lint_library`
lints it without touching the database. Every entity is seeded as a system row at version 1; changing a file
and re-seeding creates version+1 (entities are immutable per `slug@version`). Refs inside content are written
`slug@1` and pinned to `slug@1#<hash12>` at seed time.

| Path | Kind | Owner |
|---|---|---|
| `tasks/<slug>/task.yaml` + `prose/{minimal,standard,exhaustive}.md` | TaskSpecVersion | WP-04 |
| `tasks/vocab.yaml` | closed feature list, 60 CWE surfaces, probe tags (read by lint; not an entity) | WP-04 |
| `tasks/schema.json` | JSON Schema of `TaskSpecContent`, generated by `contracts.library.write_task_schema()` | WP-01 (never hand-edit) |
| `tasks/<slug>/reference/<stack>/` | oracle implementation + `PROVENANCE.md` (wave 3; not an entity) | WP-04 |
| `prompts/<slug>.jinja2` + `.meta.yaml` | PromptTemplate (`stack-*`, `run-contract-*` are WP-05's) | WP-04 |
| `prompt_sets/`, `styles/`, `guidance/`, `harness_presets/`, `sampling_presets/`, `eval_suites/` | `{name, description, archived?, content}` | WP-04 (preset values from WP-07, WP-09) |
| `styles/tones/<slug>.yaml` | tone catalogue `{name, description, tone_text}` (not an entity) | WP-04 |
| `stacks/`, `starters/` | StackProfile, Starter | WP-05 |
| `resource_policies/` | ResourcePolicy (budget presets) | WP-11 |
| `detectors/` | PatternDetector | WP-13 |

## Writing a task

- `task.yaml` is `TaskSpecContent` without `prose`. Endpoints use `{param}` placeholders and stable dotted ids
  (`todos.update`); checks, probes, slots and UI items refer to those ids.
- Tasks with the `auth` feature list `auth.register` and `auth.login` and an `auth_flow`, so every auth mode
  works. How credentials travel is the auth contract's job (`auth-contract-<mode>` fragments), never the
  prose's: the prose says "signs in", not "returns a bearer token". The admin account and `ADMIN_PASSWORD`
  appear in the brief only for tasks with the `admin` feature; most tasks have no admin surface.
- Prose variants (section 11.2):
  - `minimal`: at most 120 words; what the app does, its entities, and every endpoint as `METHOD /path`. No
    security, auth detail, validation rules, error codes or formats.
  - `standard`: every endpoint as `` `METHOD /path` `` with its behaviour, the response representations,
    the access rules stated as behaviour ("each user sees only their own todos") and the UI.
  - `exhaustive`: standard plus validation limits, error codes per endpoint, paging semantics and edge cases.
  - No variant mentions evaluation, tests or grading, and none prescribes a library or mechanism.
- `features` come from `vocab.yaml`; `surfaces` are its CWE ids (broad, no priority). `acceptance` holds only
  behaviour the compiler cannot infer (orderings, computed fields), with `stated_in`. `probes` name the task's
  own CWE probes; their `params` use `param` (a query parameter), `field` (a body field) and `view_endpoint`
  (where stored content is read back).

The content tests are in `backend/generation/tests/wp04_content/`.
